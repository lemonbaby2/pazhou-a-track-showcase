## Task1 篮球平衡：61 维本体感觉如何撑起 14 个关节

### 一句话理解

鸭子不是在执行「保持平衡」这个抽象指令，而是在 50 Hz 的闭环里反复循环：读 61 维身体感觉 → 策略网络出 14 个关节动作 → MuJoCo 推进物理 → 把新状态喂回下一次推理。平衡是这个循环稳定运转的结果，不是一个被存储的姿势。

### 模型契约

```text
obs   [1, 61]      ─┐
h_in  [1, 1, 256]   ├─> actions [1, 14]
c_in  [1, 1, 256]  ─┘   h_out / c_out [1, 1, 256]
```

actor 不是单帧 MLP，而是 `LSTM(256)` 接 `512 → 256 → 128` 的 ELU MLP。**每一拍的 `h_out/c_out` 必须传给下一拍**；只有首次启动、换策略、摔倒恢复、episode reset 才清零。这一点最容易在部署时踩坑——忘了传隐状态，鸭子会表现得像失忆。

61 维观测的分布：角速度 3 + 重力投影 3 + 关节位置 14 + 关节速度 14 + 上一动作 14 + 速度命令 3 + 头部零填充 4 + 身体零填充 6。

最关键的认知是：**球的位置和速度不在 actor 的观测里**。策略只能从陀螺仪、重力投影、关节状态和上一动作反推球的滚动趋势，这是 LSTM 存在的理由。训练时的 critic 额外拿到球的状态（privileged critic），部署时只导出 actor，所以不存在把答案泄漏给机器人的问题。

### 本机实测

| 平台 | 步数 | 时长 | 重置 | 推理均值 / P95 | 输出校验最大误差 |
|---|---:|---:|---:|---|---|
| Windows 本机（CPU 物理 + RTX 3050 Ti ONNX） | 250 | 5.0 s | 0 | 2.45 / 2.72 ms | 8.34e-7 |
| DGX Spark（Ubuntu + GPU ONNX） | 1500 | 30.0 s | 0 | 0.82 / 2.94 ms | 1.19e-6 |

两平台都做到全程 0 次终止，说明接口、时序状态、关节动作、物理环境已经接成闭环。窗口大小差 6 倍是刻意留的：小窗口证明「能跑通」，大窗口证明「能撑住」。

### 心得

这一本把我对「强化学习策略」的理解从「训练完得到一个模型」改成了「得到一个必须持续供电的控制器」。三个必须分清的东西：

1. **训练**：PPO 采样、奖励设计、critic 特权信息；
2. **部署**：只留 actor，隐状态要自己管，观测布局一个字节都不能错位；
3. **验证**：ONNX 与 PyTorch 的数值一致性（parity），和「能不能站稳」是两回事，前者过了不代表后者。

奖励函数的设计也值得记一笔：只惩罚球速，策略会学成僵硬站立；加入速度跟踪，它才会学着边换重心边让球滚。**奖励塑造的是行为风格，不只是成功率。**

### 边界声明

这是对公开 `policy.onnx` 的本机复现，不是从零训练，也没有真机验证。仿真 0 重置 ≠ 真机安全可用。

## Task2 浏览器物理扰动：拖拽不是动画，是真的施力

### 一句话理解

把策略回放搬进浏览器，用鼠标拖鸭子，看的不是特效，是 `mjData.xfrc_applied` 里的六维力/力矩经过接触求解后，如何改变整条「外力 → 动力学 → 观测 → 策略 → 动作」的闭环。

### 技术栈

- 物理：MuJoCo 编译成 WebAssembly 在浏览器里跑
- 推理：ONNX Runtime Web 跑同一个 actor
- 渲染：WebGL

构建方式：`msp build microduck`，产出 63 MB / 48 个文件的静态应用，必须通过 HTTP 静态服务访问，**不能直接双击 `index.html`**（`file://` 下 WASM 和模型都加载不了）。

### 本次操作记录

| 项 | 值 |
|---|---|
| mjswan 版本 | 0.11.9 |
| 锁定上游 | `microduck_rl@c690e55`、`microduck@590b986` |
| 构建产物 | 63 MB / 48 文件，本地 HTTP 首页 200 |
| 扰动方式 | Pull 弹簧 200 N/m、Push 脉冲 |
| 试验次数 | 3 次（右上提拉 / 左侧推拽 / 斜向摆动），每次之间 Reset |
| 录像 | 48.8 s |

关键区分：拖拽写入的是**施加在刚体上的力**，不是直接改坐标。脚能不能建立支撑、切向力多大才打滑、冲击怎么传到机身，全由接触求解决定。这就是为什么「看起来在动」和「其实在受力」是两件事。

### 心得

「出现力箭头」「姿态发生变化」「重新站稳」是三个不同层级的结论，很多人会把第一个当成第三个。

- 力箭头出现 → 说明交互链路接上了；
- 姿态变化 → 说明物理真的在积分；
- 重新站稳 → 才涉及鲁棒性，而且必须给出施力大小、方向、时长、重置条件、重复次数。

我这次只做到前两层，录像是**定性 smoke test**。要变成定量结论，至少得固定 Push 脉冲、方向和时长，导出躯干高度/倾角/足部接触时序，跑多个随机种子，最后才能报恢复成功率。

另一个容易混的坑：Task1 的篮球策略和 Task2 的 Walk 策略都是 `61 → 14`，但**形状兼容不代表能替换**。参数、场景、命令槽都可能不同。

## Task3 高跷行走：换了腿长，就是换了一个任务

### 一句话理解

同一只鸭子，把腿换成高跷，重心、步频、落脚点全部改变，原策略直接失效——形态本身就是任务的一部分，这就是课程说的「形态课程」。

### 本任务看什么

- 契约仍然是 `obs[1, 61] → action[1, 14]`，13 个命令槽在部分任务里必须零填充；
- 高跷场景的落脚面积比脚掌小，接触点容错极低；
- 训练入口和回放入口必须分开：`resume=False` 是从零初始化，`resume=True` 需要任务**完全匹配**的 checkpoint。

### 实测与一个必须说清楚的坑

notebook 执行结果：9/9 单元格完成，26.5 s，状态 `executed`、`error: null`。

但 log 里有这么一段：

```text
╭─ Invalid choice ─────────────────────────────────────────────╮
│ invalid choice 'Mjlab-Stilt-Flat-MicroDuck' for argument      │
│ 'value'. Expected one of ('Mjlab-Cartpole-Balance', ...       │
│ 'Mjlab-Velocity-Rough-Unitree-Go1').                          │
╰──────────────────────────────────────────────────────────────╯
```

**这个任务名在 mjlab 的任务注册表里根本不存在**。mjlab 内置只有 12 个通用任务（Cartpole、Lift-Cube、Tracking-G1、Velocity-G1/Go1 等），MicroDuck 的 stilt 任务没有被注册进去。所以 notebook 里那条 `--task` 调用是跑不通的。

真正的 4.81 MB 高跷视频来自另一条路：`microduck-playground-stilts` 这套独立 playground，通过 `--backend gpu` 直接加载任务专属 ONNX 做闭环。

### 心得

**«9/9 格全绿» 不等于 «每一格都成功»。** 这是这次最值钱的一条经验。

notebook 的 `executed` 只说明代码单元格跑完没崩，不说明里面的 `subprocess` 调用返回了 0。如果只看最后的 `{"status": "executed"}`，会得出「stilt 任务训练通过」的错误结论。

正确做法是三条一起看：**单元格计数 + stderr/stderr-like 输出 + 产物文件是否存在**。产物（4.81 MB MP4 + JSON）才是硬证据，日志里的异常是软证据，状态字段只能算参考。

顺带把「形态课程」这层想清楚了：换腿长不是改一个参数，是改了动力学方程里的多项系数，策略必须重学。这也解释了为什么课程反复强调「不要跨任务复用行走模型」。

## Task4 摆动旋转：不给驱动，靠关节自己把能量泵进去

### 一句话理解

Swing pump 是欠驱动系统的经典玩法——没有外部电机推身体，靠髋/腿关节按正确相位周期性伸缩，把能量一点点泵进摆动模态，让振幅自己长起来。

### 与「走路」的本质区别

| | 走路（Task3/7） | 摆动（Task4） |
|---|---|---|
| 目标 | 跟踪速度命令 | 建立稳定极限环 |
| 时间尺度 | 每步都要纠偏 | 多周期累积相位 |
| 失败形态 | 摔倒 | 摆不起来 / 相位锁死 / 过冲 |
| 关键量 | 跟踪误差 | 振幅、周期、相位差 |

摆动的难点在**相位**：能量注入必须卡在速度与位移同相的位置，早一点或晚一点都在做负功。这跟推秋千是同一件事。

### 实测

9/9 单元格，33.2 s，产物 `swing_gpu_latest.mp4` 6.69 MB。

同样遇到任务名未注册的问题：`invalid choice 'Mjlab-SwingPump-MicroDuck'`。和 Task3 是同一个根因——MicroDuck 系列任务没有进 mjlab 的注册表，notebook 里的 `--task` 路径走不通，实际视频同样来自独立 playground 的 ONNX 闭环。

### 心得

第一本是「跟踪外部命令」，这一本是「自己产生周期运动」。放在一起看才明白：RL 策略不只会做伺服，也能学出振荡器。

工程上记住一点就够了：**遇到 `invalid choice` 这类注册表错误，说明缺的是任务注册（`tasks/__init__.py` 里的 register 调用），不是模型缺权重，也不是环境缺依赖。** 报错里列出的 12 个名字就是当前注册表的全部内容，对照一下就知道差哪一行。

## Task5 球平衡（FastSAC）：换算法同时换了观测维度

### 一句话理解

同样是「球在背上」，Task1 用 PPO + 61 维 + LSTM，Task5 用 FastSAC + **54 维** + 无递归。算法换了，观测布局也跟着变，两个模型不能互相冒充。

### 硬指标（900 步实测）

| 项 | 值 |
|---|---|
| 观测维度 | **54**（对比 Task1 的 61，少 7 维） |
| 动作维度 | 14 |
| 推理调用 | 900 次 |
| 视频帧数 | 540 |
| 输出校验最大误差 | 2.68e-7 |
| 推理均值 / P95 | 4.16 / 8.23 ms |
| **失败重置次数** | **59** |
| 超时重置 | 0 |

59 次失败重置是这份数据里最该被看见的一行。900 步里重置 59 次，平均约每 15 步摔一次——这不是「跑通了」，这是「在一个很窄的容错窗口里反复失败」。

### 心得

**off-policy 的样本效率优势，是用稳定性换的。** FastSAC 从 replay buffer 里反复利用旧数据，学得快，但分布偏移时容易学出脆弱的策略；PPO 每轮只小步更新，慢但稳。这次 59 次重置就是「快而脆」的直接证据。

第二条更实用：**观测维度变了，就别想着复用归一化参数。** 61 维模型里 `0:3` 是角速度、`48:51` 是速度命令；54 维布局里这些索引全变了。ONNX 的 `[null, 54]` 和 `[null, 61]` 看着只差一个数字，接错了不会报错，只会让鸭子做出莫名其妙动作——**形状兼容 ≠ 语义兼容**，这个坑 Task2 提过一次，这里是第二次。

第三条是关于数据诚实：590 帧视频看起来是「球在背上稳住了」，但 JSON 说重置了 59 次。**只有把重置次数写在视频旁边，那条视频才有意义。**

## Task6 梯面攀爬：两套策略 + 一次握手

### 一句话理解

爬梯不是「行走策略 + 梯子场景」，而是两套策略接力：`climber.onnx` 沿交替踏棱往上爬，`getup.onnx` 爬到顶后起身。中间靠**接触检测**触发交接。

### 结构

| 项 | climber | getup |
|---|---|---|
| 作用 | 沿踏棱攀爬 | 到顶起身 |
| 观测 / 动作 | 61 / 14 | 61 / 14 |
| 命令槽 | 13 个必须零填充 | 同 |
| 本次调用次数 | 1500 | **0** |
| 输出校验误差 | 1.07e-6 | —（未触发） |

运行参数：64 个并行环境，CPU 物理，`handoff_contact_steps=1`（接触持续 1 步即交接），`spawn_noise_scale=1.0`。本次耗时 992.1 s，是 8 本里最长的一本。

### 心得

**多策略系统最脆弱的地方不是任何一个策略，是交接那一刻。** 交接判据设成 1 步接触，好处是响应快，坏处是抖动一下就切过去——真实系统里通常要加滞回（连续 N 步满足才切）。

更有意思的是 `getup` 本次调用 0 次。这意味着鸭子根本没爬到需要起身的位置。视频看着在爬，但**两套策略里只用了一套**。如果不看 JSON 里的 `getup.inference_calls = 0`，很容易误以为「双策略系统整体验证通过」。

这跟 Task3 的教训是同一条：**视频是必要证据，不是充分证据。** 判断「用了什么」，要去数调用次数，不要看画面。

另外 `command_slots_zero = true` 这个字段值得单独记：爬梯时不允许外部速度命令干扰，13 个命令槽强制置零，否则策略会把「爬」和「走」混在一起。

## Task7 RDK X5 网页与多策略 BPU 验收：没有板子，就不要假装有

### 一句话理解

这一本的目标是把 ONNX 编译成 BPU 能吃的东西（HBM），在 RDK X5 上跑真实端侧推理，并在网页上做多策略切换。**我这次没有 RDK X5 板子，所以这一本只完成了一半。**

### 实际完成与未完成

| 环节 | 状态 | 证据 |
|---|---|---|
| 环境就绪、依赖装好 | ✅ | 9/9 单元格，20.8 s |
| 本地 ONNX 契约检查 | ✅ | `obs → action` 形状与有限值检查通过 |
| GPU 闭环视频 | ✅ | `walking_gpu_latest.mp4` 5.13 MB、`perturbation_gpu_latest.mp4` 4.90 MB |
| ONNX → HBM 编译 | ⬜ 未做 | 需要板端工具链 |
| BPU 端侧推理 | ⬜ 未做 | `bpu: "not_run_no_board"` |
| 板端审计（连通 / HBM 元数据 / 服务日志） | ⬜ 未做 | 同上 |

执行记录里这一行写得很明确：

```json
{"task": "07", "status": "executed", "executed_code_cells": 9, "bpu": "not_run_no_board"}
```

### 心得

**没有硬件的时候，最专业的做法是把「已验收」和「未验收」拆开列，而不是拿 GPU 视频冒充板端结果。**

notebook 本身的设计值得学：它把 BPU 单元做成可选开关（`MICRODUCK_RUN_BPU=1`），默认关闭时不会伪造板端结果，输出标记会停在 `PASS-local-onnx` / `PASS-GPU-VIDEO`，不会给你一个假的 `PASS-BPU`。

这背后是一条通用原则：**部署链路的每一段都要有独立的通过标记**。ONNX 契约通过、GPU 闭环通过、HBM 编译通过、BPU 推理通过，四件事互不蕴含。少一段就说少一段。

如果要补，缺的是：一块 RDK X5、官方工具链、以及把 `walking_demo_latest.onnx` 编译成 HBM 后做数值对齐（BPU 的量化误差通常比 GPU 大一到两个数量级，这是下一个要面对的问题）。

## Task8 LightNav-0 视觉语言导航：让鸭子听懂一句话

### 一句话理解

前七本的输入是**人给的速度命令**；这一本的输入是**一张图 + 一句话**。中间多出来的那一大块，是「把像素和词，翻译成几何目标」的桥。

### 完整链条（这是本任务最该背下来的图）

```text
第一视角图像 + 语言指令
      ↓ WebSocket
LightNav-0（vLLM 本地推理，GPU，不训练）
      ↓ 两个空间指向通道：目标位置 / 下一步行动位置
      ↓ RVQ（残差向量量化）动作码解码
   10 × 3 局部平面轨迹（10 个位姿）
      ↓
MPC（Ipopt 非线性优化求解）
      ↓ 速度命令
行走策略（50 Hz 控制 14 个关节）
      ↓
MuJoCo 里真的走起来
```

三个场景：官方住宅（原样）、自建客厅、自建走廊。后两个重新布置了墙体、地面和家具，但**复用官方场景的真实网格资源**——这样变化只来自布局，不来自资产质量，是干净的泛化测试。

### 真实数据（三场景全记录）

| 场景 | 指令 | 预测次数 | 终止原因 | 仿真时长 | 墙钟时长 | 推理中位延迟 | 初始距离 | **最终距离** | 躯干高度 |
|---|---|---:|---|---:|---:|---:|---:|---:|---:|
| 官方住宅 | Walk to the table on your left and stop. | 37 | `model_stop` | 10.00 s | 59.2 s | 1467 ms | 2.946 m | **1.866 m** | 0.1173 m |
| 自建客厅 | Walk to the armchair in front of you and stop. | 42 | `model_stop` | 11.25 s | 71.2 s | 1713 ms | 1.811 m | **1.171 m** | 0.1179 m |
| 自建走廊 | Go straight down the hallway to the potted plant and stop. | 47 | `model_stop` | 12.50 s | 81.9 s | 1777 ms | 2.700 m | **1.218 m** | 0.1175 m |

三件事从这张表里直接读出来：

1. **三个场景全部以 `model_stop` 结束**，没有 `time_limit`，也没有 `fall`——鸭子没摔，姿态稳定（躯干高度 0.117 m，三场几乎一致）。
2. **三个场景全部没走到**，残余距离 1.17–1.87 m，和开营时说的「差 1 米以上」完全对得上。
3. **延迟随场景复杂度上升**：1467 → 1713 → 1777 ms。自建场景的延迟更高，说明模型在里面看到了更多需要处理的东西。

另一个容易被忽略的字段是 `time_mode: "simulation pauses during inference"`——**推理时仿真暂停**。所以 10 s 仿真时间要花 59 s 墙钟。这个设计让实验可复现，但也意味着真实机器人上不会给你「暂停」这个特权。

### 思考题①：多出来的「理解图像 + 理解语言」，靠的是什么？

靠的不是更强的控制器，而是**一个命令发生器**。

前七本的因果链是「人 → 速度命令 → 策略 → 关节」。第八本在前面插了一段：「图 + 词 → 模型 → 平面轨迹 → MPC → 速度命令」。所以第八本不是把前七本变聪明了，是**在策略前面接了一个会看会读的决策层**。

具体靠三样东西：

1. **视觉-语言对齐**：LightNav-0 的底座是视觉语言模型，它把「桌子」「扶手椅」「盆栽」这类词，和图像里的区域对应起来。这是纯 CV 做不到的——CV 能框出「一个物体」，但不知道那是不是「你说的那个」。
2. **空间指向**：模型不只输出「往前走」，而是输出两个空间指向通道——目标大概在哪、下一步该往哪挪。这把语言落到了几何上。
3. **轨迹解码（RVQ）**：把高维动作码解成 10 个平面位姿。注意是**局部轨迹**，不是全局路径规划——它只负责「接下来一小段怎么走」，不管整栋房子。

所以回答是：**多出来的是「语义 → 几何」的翻译能力，而不是控制能力。** 控制部分（MPC + 行走策略）和前面几本是一套。

### 思考题②：为什么「模型说停止」不等于「真的到了目标」？

三个层次的原因，从浅到深：

**第一层：`model_stop` 是模型自己的判定，没有几何校验。**

模型发停止，依据的是它从第一视角看到的画面——目标够大、够居中、大概在那个方位，它就认为到了。但它的判据来自训练分布里的相对位置关系，不是真实米制距离。**模型从来没有被要求输出「还差 1.2 米」这种量。** 报告里的 `final_target_distance_m` 是事后用真值坐标算的，模型自己不知道这个数。

三个场景 1.17 / 1.22 / 1.87 m 的残余，就是这个偏差的量化。

**第二层：相机不知道自己的尺度。**

单目第一视角图像里，「桌子占画面一半」既可能是「我离桌子 0.8 米」，也可能是「这是张大桌子，我在 1.5 米外」。鸭子只有 0.117 m 高的躯干，视点低、视场窄，尺度歧义比人形机器人更严重。

**第三层：感知频率和控制频率不同步（这条最关键）。**

- 行走策略：50 Hz，每 20 ms 出一个关节动作；
- LightNav-0：1.5–1.8 s 出一次预测，一次给 10 个轨迹点。

也就是说，模型每出一次预测，机器人要盲走 1.5 秒以上。如果这 10 个点按 50 Hz 消费，只够 0.2 秒，剩下 1.3 秒 MPC 只能靠外推。**推理时仿真暂停**掩盖了这个矛盾——真实机器人上不会暂停，这段时间里世界在变、机器人在动，模型看到的是过时的画面。

所以 `model_stop` 的本质是：**模型基于一张「已经过时 1.5 秒」的画面，判断「我大概到了」，然后停止。** 画面过时 + 单目尺度歧义 + 没有几何闭环，三者叠加，1 米级残差几乎是必然的。

### 心得

这一本给我的最大改变，是对「VLA / 导航模型」的能力边界有了具体数字感。

**它不是「更聪明的走路」，是「会说话的导航仪」。** 走路那部分（MPC + 策略）成熟得多；瓶颈明确卡在「看图说话 → 精确几何」这一段。

工程上最该记的三条：

1. **停止信号必须有独立的几何校验。** 只信模型输出，就会像这次一样停在 1 米外。生产系统里应该加一条：模型说停 → 查深度/点云/已知地图 → 距离小于阈值才真停。这是最便宜也最有效的补丁。
2. **感知-控制频率要匹配。** 1.5 s 的推理延迟配 50 Hz 控制，中间必须有可靠的轨迹外推或更快的局部避障兜底，否则延迟直接变成撞墙风险。
3. **`fall` / `time_limit` / `model_stop` 三种终止要分开统计。** 这次三场全是 `model_stop`，说明「没摔、没超时、模型自己喊停但没到」。把三种混在一起报「任务完成」，是最常见的自欺。

### 边界声明

本次使用官方预训练 LightNav-0，**不训练、不连开发板**。目标位置只用于事后测量距离，不传给导航模型，也不参与生成控制命令——这一点在 notebook 里写死了，是保证评测干净的关键。三场都没走到，结果如实保留，不挑片段。

## 八本走完，沉淀下来的六条

1. **策略是控制器，不是模型文件。** 隐状态、观测布局、控制频率，三者任何一个错位都会让鸭子「看起来在动，其实在乱动」。
2. **形状兼容 ≠ 语义兼容。** 61 维和 54 维、篮球策略和行走策略，长得像但换了就废。
3. **`executed` 不等于成功。** 9/9 格全绿的同时，日志里可能躺着一个 `invalid choice`。要同时看单元格数、异常输出、产物文件。
4. **视频是必要证据，不是充分证据。** 爬梯视频里 `getup` 调用 0 次；球平衡视频里重置了 59 次。数调用次数、看重置次数，别只看画面。
5. **没做的部分要单独列。** Task7 没有板子，就写 `not_run_no_board`，不拿 GPU 视频顶板端结果。
6. **「到达」是一个需要被定义的状态。** `model_stop` 只表示模型认为到了，实测残余 1.17–1.87 m。停止、到点、完成任务，是三件不同的事。
